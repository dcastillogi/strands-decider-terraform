# strands-decider-terraform

Terraform for serving a [Strands Decider](https://github.com/strands-labs/strands-decider) v2
model on a single GPU EC2 instance, behind an Envoy proxy that requires an API key.

Strands Decider is a decision model: it receives a state and typed questions (`noul` yes/no,
`choice`, `score`) and returns a calibrated probability for every option in one forward pass,
without generating text. The default model is
[`StrandsAgents/strands-decider-E2B-gemma4-v2-2611`](https://huggingface.co/StrandsAgents/strands-decider-E2B-gemma4-v2-2611)
(Gemma 4 E2B, 10.3 GB in bf16) on a `g6.xlarge` (one NVIDIA L4, 24 GB).

```
client ──HTTP :8080──▶ Envoy (x-api-key, RBAC) ──▶ 127.0.0.1:8001 decider server ──▶ GPU
```

## What gets created

| Resource | Purpose |
| --- | --- |
| EC2 GPU instance (Deep Learning Base AMI, Ubuntu 22.04) | Runs the model server and Envoy; no SSH, access through SSM Session Manager |
| Elastic IP and security group | Port 8080 open only to `allowed_cidr` |
| Secrets Manager secret | API key generated by Terraform, read by Envoy at start |
| SSM document and State Manager association | Installs and updates the Python runtime without replacing the instance |
| Optional load generator, results bucket | In-region benchmarking (`load_generator = true`) |

The runtime (`runtime/`) is shipped inside the SSM document. Changing its code or the
inference variables updates the association and restarts the service in place; changing the
boot script (`user_data.sh.tftpl`) replaces the instance, keeping the Elastic IP and the key.

## Requirements

- Terraform 1.4 or later, the AWS CLI, `python3` and `curl` on the machine running Terraform.
- AWS credentials through the standard chain (`AWS_PROFILE`, environment variables, SSO...).
- A VPC with a public subnet, and a G/VT instance quota of at least 4 vCPUs in the region.

## Deploy

```sh
cp terraform.tfvars.example terraform.tfvars   # set allowed_cidr, vpc_id, subnet_id
terraform init
terraform apply
```

`allowed_cidr` is the only network allowed to call the endpoint; to allow just your current
address use `"$(curl -s https://checkip.amazonaws.com)/32"`. With `wait_for_ready = true` (the
default), `apply` waits until the runtime is installed, the model is loaded and an
authenticated request succeeds through Envoy, so the machine running Terraform must be inside
`allowed_cidr`. A first deployment takes about 10 to 15 minutes, mostly package and model
downloads.

The instance bills until it is destroyed:

```sh
terraform destroy
```

## Call it

```sh
./scripts/infer.sh                         # sends examples/triage.json
./scripts/infer.sh path/to/request.json
```

Or with curl:

```sh
SECRET=$(terraform output -raw api_key_secret_arn)
KEY=$(aws secretsmanager get-secret-value --secret-id "$SECRET" --region "$(cut -d: -f4 <<<"$SECRET")" \
  --query SecretString --output text | python3 -c 'import json,sys;print(json.load(sys.stdin)["key"])')
curl -s "$(terraform output -raw endpoint)" -H "x-api-key: $KEY" -H 'content-type: application/json' -d '{
  "state": "Help! My payouts have been failing for 3 days!",
  "questions": {
    "urgent": {"type": "noul", "instructions": "Does this convey urgency?"},
    "team": {"type": "choice", "instructions": "Which team should handle this?",
             "criteria": {"billing": null, "sales": null, "retail": null}}
  }
}'
```

Besides the upstream fields (`model`, `answers`, `usage`), every response includes
`queue_ms`, `inference_ms`, `latency_ms` and `batch_size` from the server. `GET /healthz`
needs no key and only reports that Envoy is up.

## Configuration

| Variable | Default | Meaning |
| --- | --- | --- |
| `model_id` | `StrandsAgents/strands-decider-E2B-gemma4-v2-2611` | Any Strands Decider v2 checkpoint that fits the GPU |
| `instance_type` | `g6.xlarge` | `g6.xlarge`, `g6.2xlarge`, `g5.xlarge`, `g5.2xlarge` or `g6e.xlarge` |
| `inference_batching` | `true` | Batch concurrent requests together on the GPU (see below) |
| `inference_max_batch` | `8` | Requests per GPU batch |
| `inference_batch_wait_ms` | `2` | How long the batcher waits to fill a batch |
| `inference_max_batch_tokens` | `8192` | Padded tokens per forward pass; longer prompts use the upstream path |
| `inference_queue_size` | `256` | Requests waiting beyond the batch; past it the server answers 503 |
| `model_processes` | `1` | One or two model copies on the GPU |
| `hf_token_secret_arn` | `""` | Secrets Manager secret with a Hugging Face token, for gated models |
| `load_generator` | `false` | Create the in-region load generator and its results bucket |

The E4B model (16 GB) needs a GPU with 40 GB or more, such as `g6e.xlarge` (L40S, 48 GB).

## How serving works

The pinned [`strands-decider` 0.4.0](https://pypi.org/project/strands-decider/0.4.0/) package
answers one request per forward pass: it encodes the state once and runs that request's
questions in a batch over it. Requests from different clients do not share a pass.

`runtime/batch_engine.py` adds cross-request batching. Requests arriving within
`inference_batch_wait_ms` of each other are grouped, up to `inference_max_batch`. Every
(request, question) prompt of the group runs in one full forward pass, under a per-row
prefix-bidirectional mask that is equivalent to upstream's attention: state tokens see the
state, question tokens see the state and their own question, and no token sees padding. The
rendering, the readout and the calibration are upstream's own functions. A full pass per
question is upstream's reference mode (`reuse_state=False`).

- Requests with images, and requests whose prompts exceed `inference_max_batch_tokens`, go
  through the upstream engine unchanged.
- Prompts are sorted by length before being split into forward passes, so short prompts are
  not padded to the length of long ones.
- bf16 results can change slightly with the batch shape. A `choice` question whose two best
  options are less than 0.05 apart is recomputed alone, in upstream's reference shape, so that
  neighbouring traffic cannot decide close calls.
- A CUDA out-of-memory error splits the batch in half and retries.
- Admission is bounded: when `inference_queue_size + inference_max_batch` requests are pending,
  new ones get HTTP 503 with `Retry-After: 1`.

The tests in `tests/` build a small random Gemma 4 checkpoint with the E2B layout and the real
E2B tokenizer, load it with upstream's loader on the CPU, and check that batched answers equal
upstream's `DecisionEngine` answers, request by request.

## Tests

Unit tests (CPU, no AWS):

```sh
uv run --with strands-decider==0.4.0 --with torch==2.14.1 --with transformers==5.23.0 --with httpx \
  python -m unittest discover -s tests -v
terraform fmt -check && terraform validate
```

Against a deployment, from the machine running Terraform:

```sh
scripts/smoke-test.sh "$(terraform output -raw endpoint)" "$(terraform output -raw api_key_secret_arn)"
python3 scripts/latency-probe.py        # unloaded latency by request shape
python3 scripts/load-test.py            # closed-loop load, concurrency 1 to 32
python3 scripts/overload-test.py        # 503 backpressure and recovery
python3 scripts/verify-answers.py capture   # then, after a change: compare
```

These include the client's own network. For measurements of the service alone, set
`load_generator = true` and run the same tools from a CPU instance in the same subnet, against
the private address:

```sh
python3 scripts/benchmark.py latency-probe
python3 scripts/benchmark.py load-test --telemetry -- --concurrency 1,2,4,8,16,32,64 --seconds 60
python3 scripts/benchmark.py overload-test
```

`benchmark.py` copies `scripts/` and `examples/` through the results bucket, runs the tool on
the load generator over SSM and extracts its results under `deployment-results/runs/`. With
`--telemetry` the decider instance records CPU, GPU, VRAM and power each second, summarized
per load stage.

Debugging on the instance:

```sh
aws ssm start-session --target "$(terraform output -raw instance_id)"
# systemctl status strands-decider envoy; journalctl -u strands-decider; nvidia-smi
```

## Security notes

- The endpoint is plain HTTP. Put TLS in front (an ALB with ACM, or TLS in Envoy) before sending
  sensitive data, and keep `allowed_cidr` narrow.
- The API key is generated by Terraform and therefore stored in the state. Use an encrypted
  remote backend with restricted access.
- The instance has no SSH key; administration is through SSM Session Manager.
